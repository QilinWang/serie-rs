# Independent evidence review: SERIE-RS window benchmark

Reviewed on 2026-11-04 by a separate Codex reviewer. Scope: the benchmark design, `benchmarks/window/benchmark.py`, `runner.rs`, both JSON records, the draft benchmark report and the root README. I did not run the benchmark or compile the code.

## Verdict

The observations support publishing the measured single-operation timings and the reproducible harness as **exploratory, high-variation results**. They do not support a stable Rust-versus-NumPy or Rust-versus-Numba speedup or a ranking in the project headline. A homepage link to the fully qualified report is appropriate. No conclusion about total SERIE, the active Fern pipeline, model training, or cross-machine performance follows from these measurements.

## Evidence and arithmetic

- Both records report identical source, input and X/Y SHA-256 values, one pinned logical CPU (`[4]`), 15 recorded timings per implementation and two opposite orders. Their source and harness SHA-256 values match the inspected files. The NumPy reference, separately generated Rust output and Numba first-call output are checked for shapes, values and full-byte digests by the benchmark. Timed outputs are not individually validated.
- The unique synthetic float32 input is `[36000, 3]`; outputs are contiguous X `[35841, 96, 3]` and Y `[35841, 64, 3]`, 68,814,720 bytes together. The Rust harness compiles the verbatim source-extracted function separately with `rustc -C opt-level=3`, not as the Cargo release crate. Allocation and copying are inside the timed interval; process launch, output verification, destruction and first Numba compilation are outside it.
- `run-a.json` (Rust first): Rust median 76.93 ms, range 21.81–2,293.28; NumPy median 1,337.50 ms, range 634.95–5,793.75; Numba median 18.88 ms, range 16.06–410.51.
- `run-b.json` (Rust last): Rust median 18.47 ms, range 16.64–26.69; NumPy median 49.44 ms, range 17.84–880.71; Numba median 20.40 ms, range 16.71–28.98. All medians and endpoints were independently recomputed from the recorded 15 samples.
- Median ratios change materially with the run: NumPy/Rust is approximately 17.39 and 2.68; Rust/Numba is approximately 4.07 and 0.91. Those are ratios of separately measured group medians, not paired measurements. They are evidence against advertising a repeatable speedup, not evidence of its true magnitude.
- The recorded 1-minute system load averages are 27.05 and 20.12; host notes report 10 visible logical CPUs. This and the sample spread show high load and unstable timing, but load average includes uninterruptible I/O and does not independently identify CPU contention as the cause. Different measurement order and other workload changes remain possible explanations.
- The additional NumPy view creates a different output representation without materializing the data. Its timing does not include consuming the views; the active Fern training data path uses Torch strided views, not this materialized NumPy reference. A headline must not present the view time as an equivalent copying comparison.

## Draft corrections requested

1. Replace “Every X and Y was checked” with wording that identifies the separately validated Rust and Numba outputs; the outputs produced during the timed loop are not individually checked.
2. Replace “the recorded machine was heavily contended” with “high system load and large timing variation” or similar. CPU contention is a plausible contributing explanation, not a measured attribution. The full report already correctly says it may influence the spread.
3. The opening's “less variable of two runs” should preferably say “the run with lower Rust variation”: the NumPy timings in that run still range from 17.84 to 880.71 ms. Including the full table as drafted is necessary context.

The remaining reported numbers, source-extraction boundary, zero-copy distinction, one-core scope, JIT separation, full-sample links and recommendation against a speedup headline are supported. Before a stronger claim, repeat on a low-contention, specified machine using the same correctness and timing boundaries, inspect run-to-run distributions under multiple orders, and retain all samples. This review does not assert the cause of the current variance.

## Resolution

All three requested wording changes were made before publication. The README
links this exploratory report without advertising a speedup.
